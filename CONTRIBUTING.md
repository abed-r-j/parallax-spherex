# Contributing to ParallaX

Thank you for looking. ParallaX is a small project with two halves: a Python pipeline
(`pipeline/`) and a static web app (`web/`). This page says how to set up, test, add a field
and, most useful of all, report a false alarm.

## Setup

You need Python 3.11 or newer with [uv](https://docs.astral.sh/uv/) and Node.js 22 or newer.

```bash
cd pipeline
uv sync                    # creates pipeline/.venv with the package and the dev tools
uv run parallax --help

cd ../web
npm install
npm run dev                # development server with the published data packs
```

On Windows, if a compiled Python package is blocked by Smart App Control, do not switch the
protection off; pin the previous version of that package instead.

## Tests and checks

Run these before opening a pull request. They need no network.

```bash
cd pipeline
uv run pytest -q                        # 120 passed, 2 skipped
uv run ruff check src scripts tests

cd ../web
npm test                                # 55 passed
npm run lint
npm run build
```

Two Python tests call live services and are skipped by default; run them with
`PARALLAX_NETWORK=1` set. Run these checks locally before you
push. A GitHub Actions workflow with the same checks (`.github/workflows/ci.yml`) is provided
and is started by hand from the Actions tab; it does not run on push.

## Style

* Python: `ruff` with the settings in `pyproject.toml` (line length 100). Type hints on public
  functions. A module docstring that says what the module does in plain words.
* TypeScript: strict mode, `eslint` clean with zero warnings. Pure functions go in
  `web/src/lib/` with a test next to them; components stay thin.
* Words: plain English that a non-astronomer can follow. Say what was measured, with its
  uncertainty and its caveat. Do not write that anything was "discovered".
* Numbers: every number in a document must come from `docs/RESULTS.md` or be regenerated by
  `pipeline/scripts/run_ledger.py` or `run_validation.py`. If your change moves a number,
  update `docs/RESULTS.md` in the same pull request and say why.
* Data format: the web app and the pipeline only meet in `docs/DATA_CONTRACT.md`. Change the
  contract, the writer (`export.py`) and the reader (`web/src/lib/decode.ts`, `types.ts`)
  together.
* Network manners: one request at a time to JPL services, cached answers, an honest
  User-Agent, no personal data in any request.
* SI disclosure: if an SI (AI) assistant helped write a file, keep or add the one-line
  disclosure in its header.
* No NASA, JPL, Caltech, IPAC or Space Apps logos or mission patches anywhere.

## Add a field

1. Download the cutouts (resumable; run it again later to pick up new images):

   ```bash
   cd pipeline
   uv run parallax fetch myfield --ra 202.4696 --dec 47.1953 --name "My field" --size-arcmin 6.25
   ```

   This registers the field in `data/extra_targets.json`. For a star with a known proper
   motion, add it to `pipeline/src/parallax/targets.py` instead, with its catalogue position,
   epoch and motion, so that the catalogue marker follows it.
2. Build the pack: `uv run parallax publish myfield`. It writes
   `web/public/data/myfield/` and adds the field to `index.json`.
3. Look at it: `uv run parallax serve`, then open `http://127.0.0.1:8000/?field=myfield`.
4. If the field should carry ledger numbers with injection tests, run
   `uv run python scripts/run_ledger.py myfield` first (a few minutes), then publish again.

Keep fields small (6 arcmin is the default). The top-level `data/` folder is
git-ignored; the packs under `web/public/data/` are committed (about 100 MB in total), so
commit a new pack only if it should ship with the site.

## Report a false alarm

A detection or candidate that is not real is the most valuable report you can send, because
the project's main claim is a false-alarm rate. Open an issue titled "False alarm: <field>"
with:

* the link to the exact view (the Share button gives it; it carries field, frame, mode and
  the picked pixel);
* the candidate id or the frame number and pixel, and the class the tool gave it (`mover`,
  `variable`, `motion-dipole`, `chromatic`, `star-residual`, `artifact`);
* why you think it is not real. The usual causes are: a cosmic ray or hot pixel (present in
  one frame, absent in the exposure of the same detector about two minutes later); a colour
  residual (sits exactly on a catalogued star and its sign follows the star's spectrum); a
  pixel-sampling residual on a bright star; a saturated or flagged core; the edge of the
  detector;
* a screenshot if you can.

The reverse is just as welcome: a real change that the tool classed as an artifact. If you
think you have found a new moving object, check the "Known solar-system objects" overlay
first and remember that almost everything SPHEREx can see moving in single frames is already
catalogued.
